# CLAUDE.md — @ragtechdev/pixel-sprites (packages/pixel-sprites)

The repo-wide rules in the root `CLAUDE.md` (hard rules, supply chain, releases, working agreement, definition of done) apply here too. This file holds what is specific to the sprites library. Paths below are relative to `packages/pixel-sprites/` unless they start with `studio/`, `scripts/` or `.github/`. Commands are run from the repository root.

## What this is

A TypeScript library that composes and renders pixel-art avatars, tiles, objects, icons and small worlds from string-based masks and fixed palettes.

## Current state (core and Sprite refactor done)

- Entries: `@ragtechdev/pixel-sprites` (pure core: `buildAvatar`, `buildTile`, `avatarKey`, `createCache`, `toSvg*`, style and palette tables), `@ragtechdev/pixel-sprites/canvas` (`paintRaster`, `drawRaster`) and `@ragtechdev/pixel-sprites/react` (`Avatar`, `Tile`, `Icon`, `WorldObject`, `World`, `PixelImage`). React is an optional peer.
- `Sprite` (`src/core/sprite.ts`) is the single image primitive: palette-slot indices plus an origin. Avatar shape masks are still `"0"`/`"1"` strings, auto-shaded by `shadeMask` using `src/core/lighting.ts`. Tile masks are `"0"`/`"1"` layers painted in named colours, resolved through the fixed `tilePalettes`. `composeSprites` (internal) produces a colour-resolved `Raster`.
- `resolveAvatarConfig` replaces any value that isn't in the fixed tables with its default.
- Size: the README's "By the numbers" table (generated by `pnpm stats`: minified and gzipped, for an app that imports only that part) is the baseline to compare against. The 3.3 KB figure this file used to quote predates the Sprite refactor and the avatar views, hair and icons added since, and is obsolete. `pnpm size` measures whole built entries instead.

- Worlds (`src/world/`): terrain tiles, tilesets, maps and objects.
  - `defineTileSet` (2×2-tile blocks plus `solid`/`water`/`grass` tile-id lists), `defineMap` (one character per block, plus placed objects), `buildMap` (memoised raster), `queryCell` and `tileAt`. Built-in tilesets are `townTileset` and `houseTileset`.
  - Art is one `*.mask.ts` file per mask under `src/world/masks/`, like the avatar masks: `masks/tiles/<tile>/<layer>.mask.ts` for terrain layers, `masks/tiles/edges/**` for edge strips, and `masks/objects/<object>/<part>.mask.ts` for objects (a directory when there are several masks, a single file otherwise). Every mask is `"0"`/`"1"` rows. Assembly lives in `src/world/tiles/tileDefs.ts` (tiles: which layer is painted in which colour name) and `src/world/objects/objectParts.ts` (which mask, ramp and offset each object part uses).
  - Tile colours are only ever named (`TileColor`), never written in art. `src/world/tiles/palettes.ts` holds the fixed palettes (`tilePalettes`: `spring`, `summer` (the default), `autumn`, `winter`), so `buildTile(id, theme)` and `buildMap(map, theme)` recolour the whole terrain. Unknown themes (including the old name `default`) fall back to summer. Objects keep their own `objectRamps`.
  - A tile is a *material* (a base colour plus 0/1 detail layers) or an *edge tile* (an inner material with edge strips painted on the open sides, where a strip can paint another tile's pixels, such as grass outside a pavement). One strip set serves every side and corner. `test/fixtures/tile-golden.json` pins every tile's pixels in the default palette.
  - Edges are tiles too: nine-patch sets (centre plus edges and corners) for `roof_*`, `beige_pavement_*` (against grass) and `wall_*` (left, right, base). `townTileset` blocks assemble them with phone-keypad keys (`1`-`9` roof, `< = >` one-block roof, `A`-`I` pavement, `l h r` wall and `[ _ ]` one-block wall with foundation). Edge tiles keep their base tile's pattern away from the edge, which the tests check.
  - Things that stand on terrain (tree, fence, door, window, counter, bookshelf, rug, flower) are **objects**, not tiles: `"0"/"1"` shape masks, auto-shaded by `shadeMask` with the fixed `objectRamps`, with footprint and behaviour in `objectInfo`. This is the base for furniture, decor and a pet. In `townTileset` water is listed as `solid` as well as `water`, so `queryCell(...).solid` already covers it and a game's movement code needs no special case.
  - Buildings (`src/world/buildings.ts`, `src/world/buildings/`) are their own thing, not tiles and objects: a house in the conventional pixel-art view (from the front and well above: the facade is visible below a roof that shows its left and right slopes and its far end). They are split by what is drawn: `config.ts` (the fixed lists, `resolveBuildingConfig`, `randomBuilding`), `frame.ts` (the measurements and ramps one building is drawn to), `wall.ts` and `roof/` (the two things whose size depends on the config, so they are generated: polygons and rectangles rasterised by `shapes.ts`, shaded with `shadeMask` and textured with repeating patterns; the roofs are one file per family, seen from above and in front: `ridged.ts` (gable, saltbox, hip and the roof behind a front wing), `flatTop.ts` (hipFlat, mansard), `gambrel.ts` and `flat.ts` (a floor of square tiles inside a thick parapet of coping stones) and `rooftop.ts` (what is on the flat part of a roof: air conditioners and vents, an air-handling unit, boxes, skylights, solar panels or a garden, all from masks; each thing is put on through one packer that keeps it on the area and clear of the things before it, and the area gives the side the chimney is on to the chimney, so nothing on a roof overlaps; with a front wing the chimney stands in the margin beside it, where the roof behind shows); each step of `depth` adds a tile of roof further up the picture, since the view is from above), `volumes.ts` (a building is one volume, or two with a wing: a `front` wing is a narrower volume in the middle that sticks out two tiles in front, drawn over the main part and holding the door; a `left` or `right` wing is a lower one-storey volume beside a two-storey main part that holds the door, each a whole building with a complete roof, their walls running out to the join (`joined` in the volume's config) with the outline and edge shading opened there, so the ground floor is one wall, and the taller part's corner is a line straight down beside the lower roof, from where the side of its roof starts to the lower roof's eave (a dark line along the join with a line of the wall's shadow tone beside it), with a flat lower roof's floor running up to it with no parapet on that side  `buildingFootprint` is made from the volumes, so the ground beside a wing is open), `facade.ts` (where the windows, door, steps and barrels go) and `parts.ts` (the catalogue of fixed-size parts and where each sits from its anchor). `draw.ts` draws them back to front and caches. Every part that is one fixed size is a mask under `src/world/masks/buildings/<part>/` (door, window, shutter, flower box, chimney, barrel, steps, round window; directory names are `houseDoor` and `houseWindow` so export names stay unique among the objects'), with detail masks (grooves, glint, slats, mortar, hoops) painted flat in one tone of the part's ramp. `defineMap` takes placed buildings as a fourth argument (`{ config, x, y }` in tiles): walls and roof are solid (`#`), the tile at the foot of the door is open with `door` set (`D`), and `buildMap` draws them with the standing objects. `LICENSE-ART.md` lists the generated roofs and wall (`roof/`, `wall.ts`); the masks are covered by `src/world/masks/**`. A `PlacedObject` may also carry a validated `color`.
  - The layering (tile, block, tileset behaviour lists, map) follows pret/pokered, with none of its art or data. Masks are made by the maintainers and by coding agents, and the art may be refined over time.

Next: more objects and a pet on `Sprite`; more tile types and objects; a Web Worker only if measurements show it's needed.

## Target design

1. **Zero-dependency, tree-shakeable ESM core** (pure TypeScript, no React, no DOM types in the core entry). The React/Preact component is a separate optional entry point (`@ragtechdev/pixel-sprites/react`), with React as an optional peer dependency.
2. **One `Sprite` abstraction** shared by avatars, tiles, furniture, decor and a pet: a palette-indexed mask plus size and anchor. Replace the three mask formats with this one.
3. **Render once, reuse.** Paint each unique config to an offscreen canvas or sprite sheet, cache by a hash of the config, and draw with `image-rendering: pixelated`. Keep a plain SVG path for non-canvas use if it is cheap. Move batch generation into a Web Worker with `OffscreenCanvas` only if it measurably blocks the main thread.
4. **Framework-agnostic API.** The consumer app mounts a canvas module outside its UI framework, so the core must be callable without any framework.
5. Stay in TypeScript. Rust/WASM is not justified for compositing small masks.

## Library commands

Run from the repository root; each is forwarded to this package.

```sh
pnpm build         # tsup (tsup.config.ts): index, canvas, react entries
pnpm typecheck     # tsc on the package + no-DOM check of the core entry (tsconfig.core.json)
pnpm test          # builds, then node:test against dist (test/*.test.mjs)
pnpm size          # gzipped size per built entry (scripts/size.mjs)
pnpm new           # scaffolding wizard for new art (scripts/new.mjs)
pnpm docs:images   # re-renders docs/images (banner, icons, avatars, tiles, objects, themes) from the built package (scripts/render-docs.mjs)
pnpm stats         # rebuilds, re-renders the images, then updates the counts and bundled sizes in the README (scripts/stats.mjs); --check only verifies the counts
pnpm check:masks   # validate every mask: 0/1 only, rectangular, tile and icon size limits, naming, orphans (scripts/check-masks.mjs)
```

Tests use the built-in `node:test` runner (no test dependency). `test/golden.test.mjs` checks `buildAvatar` pixel-for-pixel against fingerprints recorded from the original React renderer (commit db0a2c2). Add tests for each module you refactor.

## Measuring size

Build with tsup (ESM, minified, React external) and gzip the output. Report gzipped bytes for the core entry alone, the React entry alone and the whole thing (`pnpm size`), and for any part you touched as an app would import it (`pnpm stats`, which updates the README table). Compare to the numbers in that README table.

## Adding an icon, garment, hair style, object or tile

Use the scaffolding wizard instead of creating the files by hand. It puts the mask files in the right folder with the right names, and prints the exact edits still needed.

1. Run `pnpm new --dry-run` first to see what it would create. Run `pnpm new` to write the files. It is interactive; to drive it without a terminal, pipe the answers in one per line (an empty line takes the default): `printf '4\nlamp\n1\n2\n1\n\n\n\n' | pnpm new`. Menus are numbered, so run it once interactively or read `scripts/new.mjs` to see the prompt order for your kind.
2. It only creates placeholder masks (filled rectangles, or blank layers for tiles). You may draw the real masks yourself. Check the result by running `pnpm check:masks` and rendering it (`pnpm docs:images`, then look at `docs/images/`), and tell the maintainer which masks are new so they can review the look.
3. Make every edit it lists: type unions, table entries, tests, and the README table for icons. It never edits existing files and never overwrites one.
4. Add the new mask paths to `LICENSE-ART.md` if they are not already under a covered folder, then run `pnpm typecheck && pnpm test`. A new tile also needs its fingerprint in `test/fixtures/tile-golden.json`. Run `pnpm check:masks` after adding or editing any mask. After wiring a new icon, tile, object or avatar style in, run `pnpm stats` and commit the README and `docs/images/`: `pnpm test` fails when the README counts are stale.
5. Edge and nine-patch tiles are not scaffolded. Edit `src/world/tiles/tileDefs.ts` by hand.

The human-facing version of these steps lives in `CONTRIBUTING.md` at the repository root. Keep the two consistent when the wizard changes.
